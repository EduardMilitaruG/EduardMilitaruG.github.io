Helpdesk API: an API quality case study

An IT helpdesk ticketing REST API that I built and then tested in seven layers. The API is deliberately realistic, with roles, a status workflow, SLA deadlines and optimistic concurrency, because those are the places where real bugs hide. Along the way the layers found 11 real defects, and each one now has a regression test.

What the API does

  • Roles: requesters open tickets about their own problems; agents triage and resolve them.
  • Workflow: open → in_progress → waiting_on_customer → resolved → closed, with role rules (a requester can cancel, reply, accept or reopen, never resolve).
  • SLA: deadline from priority (urgent 4h, high 8h, normal 24h, low 72h), frozen at resolution.
  • Concurrency: ETags on every ticket; edits need If-Match (428 if missing, 412 if stale).
  • Privacy: other people's tickets return 404, not 403, so ticket ids cannot be probed; internal agent notes never reach requesters.

Seven quality layers

1

Static checks

Types compile and the OpenAPI spec passes Spectral with a custom ruleset (every secured operation documents 401, response arrays are bounded).

tsc · Spectral
2

Unit and property-based

Workflow invariants hold for any input: nothing leaves closed, no self-transitions, a requester can never do more than an agent, closed is reachable from every status, and a higher priority never gets a later deadline.

Vitest · fast-check
3

Integration on real PostgreSQL

Filters, pagination, LIKE escaping, the audit trail and race conditions: 10 agents resolve the same ticket at once and exactly one wins. Migrations stay safe when several replicas boot at the same time.

Vitest · Supertest
4

Contract

Every route is in the spec and vice versa. Every response is validated against the spec at runtime in tests, and a deliberately drifted spec proves the guard turns drift into failures.

express-openapi-validator
5

Security (OWASP API Top 10)

BOLA/IDOR on all 6 ticket routes, JWT alg=none, tampered and expired tokens, mass assignment, SQL injection, user enumeration, brute-force rate limiting, security headers, no stack traces.

Vitest · Supertest
6

Property-based fuzzing

Generated requests in coverage, fuzzing and stateful phases. Checks that the server never returns 500, valid requests are accepted, invalid ones are rejected, and responses match the contract.

Schemathesis
7

Load and DAST

k6 runs a mixed scenario (15 requesters + 5 agents) with p95, p99 and error budgets. OWASP ZAP runs an authenticated API scan driven by the spec, and the build fails on any alert rated Low or above.

k6 · OWASP ZAP

The pipeline

✓ static     tsc + Spectral (custom rules)
✓ tests      131 Vitest tests on a Postgres service container, coverage gate 90%
   ├─ ✓ fuzz   Schemathesis --checks all, stateful        (fresh Docker stack)
   ├─ ✓ load   k6: p95 < 300 ms, p99 < 800 ms, errors < 1%  (fresh Docker stack)
   └─ ✓ dast   OWASP ZAP API scan, gate on Low+            (fresh Docker stack)

Every job publishes its report as an artifact (JUnit, coverage, Schemathesis, k6 summary, ZAP HTML), and a weekly scheduled run catches dependency drift. The JUnit artifact feeds my other project, flaky-hunter, which flags flaky tests across CI runs.

Design decisions I can walk you through

  • 404 instead of 403 for other people's tickets: a 403 confirms that the ticket exists.
  • Row locks plus ETags: SELECT … FOR UPDATE serialises transitions, and ETags protect edits across a person's read-think-write cycle.
  • Response validation on in tests, off in production: contract drift is caught where it is cheap, with no per-request cost in production.
  • Equal-time login failures: unknown emails still run a bcrypt comparison, so timing does not reveal which accounts exist.
  • Constraints in the database too: a bug in the API still cannot write an invalid status.
